總覽

登入用 Better Auth，這是一個跑在後端程式裡的登入套件，帳號和登入狀態存在同一個 PostgreSQL。這一頁講 Better Auth 怎麼設定、對外開哪幾條路徑、它的錯誤怎麼變成我們的格式，以及團隊用來重設密碼的指令。每一次請求的登入檢查（requireAuth）屬於請求管線，註冊屬於 Account，這裡只在用到時提一句。這頁拆成 6 段，每段都有三格：要解決的問題、怎麼做、為什麼這樣做。

段落要解決的問題做法檔案
1 設定與登入憑證用使用者名稱加密碼登入，不寄信，前後端網域不同Better Auth 加 bearer、username 外掛，關掉公開註冊auth.ts
2 開放的路徑Better Auth 預設開很多路徑，PWA 只用得到三條自己寫白名單，其他回 404auth.ts
3 錯誤轉換Better Auth 的錯誤格式和我們不同，登入失敗不能說哪裡錯authError 依序判斷，轉成 AppErrorauth.ts
4 擋猜密碼同一個來源短時間內不能一直試密碼Better Auth 內建 rateLimit，登入每個 IP 每分鐘 10 次auth.ts
5 帳號資料表存帳號和登入狀態，刪帳號時連帶刪資料四張表放進我們自己的 migration001_m0.sql
6 團隊重設密碼沒有 email，忘記密碼要由團隊人工處理團隊電腦上跑的指令，確認後換成臨時密碼reset-password.ts

1 設定與登入憑證

要解決的問題

使用者用「使用者名稱加密碼」登入，系統不寄任何信，所以帳號沒有真的 email。PWA 和後端在不同網域，登入憑證要能跨網域帶過來。帳號只能由後端建立，不開放公開註冊（TS-003 §5.1、TS-001 §5.1）。

怎麼做

auth.ts:21-68 呼叫一次 betterAuth({...})，把所有設定放在一起，下表列出和這一段有關的項目。登入成功後，PWA 拿到一組 token，之後每個請求帶在 Authorization: Bearer 標頭裡。伺服器用 token 去 sessions 表找到對應的 session。session 是一列資料，代表「這支手機已登入」。

這樣做的結果

  • 登入回應的 body 裡有 token，不使用 cookie（test/m0-db.test.ts 的登入測試）。
  • 使用者名稱註冊後不能改，這件事設了 immutableUsername，但 Better Auth 1.7 遇到 bearer token 時這個檢查不生效。真正擋住改名的是第 2 段不開放 update-user（auth.ts:38-40、ADR-0107）。
  • 註冊在伺服器端呼叫 auth.api.signUpEmail，不受 disabledPaths 影響（auth.ts:1-3、ADR-0106），詳細屬於 Account。
  • 沒設 DATABASE_URL（不碰資料庫的測試）時，啟動不檢查表（auth.ts:56-57）。
  • 每個請求的登入檢查用 auth.api.getSession 查 session（middleware.ts:51-59），屬於請求管線。

為什麼這樣做

  • Bearer token，不用 cookie：前後端網域不同，不同網域的 cookie 算第三方 cookie，iPhone Safari 預設會擋，使用者可能一直被登出（ADR-0002 的 ADR-0009 段）。
  • bearer 排第一個：先把 token 換成 session（auth.ts:32）。
  • Better Auth 自己用 pg 連線池：Better Auth 不支援 Bun.sql，連的還是 app 帳號（auth.ts:22、ADR-0002 的 ADR-0003 段）。
  • email 填佔位值：username 外掛要靠 email 加密碼的帳號機制，系統又不寄信（auth.ts:29）。
  • 關掉 displayUsername：顯示名稱是 M2 自己的欄位，避免有兩個「顯示名稱」（auth.ts:41）。
  • 表名用複數：user 是 PostgreSQL 的保留字（auth.ts:51、ADR-0106）。
  • 讀 cf-connecting-ip：請求都經過 Cloudflare Tunnel，真實 IP 在這個標頭（auth.ts:59-60）。
  • 365 天沒用才過期、每天第一次使用時延長：文件沒寫理由，TS-001 §7 只把它列為 v0 想法（auth.ts:48-49）。
  • 使用者名稱 4 到 20 字、密碼 8 到 128 字：文件沒寫理由，TS-003 §7 只把它列為 v0 想法（ADR-0106）。

2 開放的路徑

要解決的問題

Better Auth 的處理器預設開很多路徑，例如 update-user（會改到使用者名稱，TS-003 §2 規定註冊後不能改）、sign-in/email、list-sessions。PWA 用得到的只有登入、登出、改密碼。

怎麼做

authRoutes（auth.ts:75-82）接住 /api/auth 底下的每個請求，去掉前綴後組成「方法 路徑」，例如 POST /sign-out。這個字串不在 OPEN 集合裡就丟 NOT_FOUND（auth.ts:77），在的話才交給 auth.handler（auth.ts:79）。OPEN 裡有 3 條（auth.ts:73）。

這樣做的結果

  • authRoutes 掛在登入檢查前面（app.ts:53-54），這 3 條請求不經過 requireAuth 和防重複寫入（app.ts:57）。登出和改密碼的 token，由 Better Auth 自己驗。
  • 測試確認 update-user、sign-up/email、sign-in/email 回 404（test/m0-http.test.ts 的「登入檢查」段）。
  • /sign-up/email 同時被 disabledPaths（auth.ts:46）和白名單擋，白名單先擋。
  • 登出後，原來的 token 打需要登入的路徑回 401（test/m0-db.test.ts）。
  • 同一個前綴下，M2 的註冊路由掛在 authRoutes 前面（app.ts:53），屬於 Account。

為什麼這樣做

  • 用白名單，不用 disabledPaths 一條條關：Better Auth 新版多出來的路徑會自動開放，白名單比較安全（ADR-0107）。
  • 不整個處理器直接掛上去：update-user 能改名稱，錯誤格式也不一致（ADR-0107）。
  • 不過登入檢查：登入時還沒有 token（ADR-0107）。
  • 不帶 Idempotency-Key：防重複寫入的紀錄是「某個人加某把 key」，要支援就得多一張沒有擁有者的表。登出第二次沒有 session 可刪，改密碼第二次因為舊密碼已不對而被拒，結果和 PRD-001 §10 要的一樣（ADR-0957）。

三條開放的路徑

路徑做什麼測試怎麼呼叫
POST /api/auth/sign-in/username登入，回 token不帶 token（test/m0-db.test.ts）
POST /api/auth/sign-out登出帶 Authorization: Bearer
POST /api/auth/change-password改密碼，body 有 currentPassword 和 newPassword帶 Authorization: Bearer

3 錯誤轉換

要解決的問題

Better Auth 回的錯誤不是我們的格式（TS-001 §5.6），PWA 無法統一處理。登入失敗時，也不能讓人從訊息分辨是使用者名稱不存在還是密碼錯（TS-003 §5.3）。

怎麼做

authRoutes 拿到 Better Auth 的回應後，成功就原樣回（auth.ts:80），失敗就交給 authError（auth.ts:85-104）。它讀回應 body 裡的 code，再依下圖的順序判斷，第一個符合的就用。結果是 AppError，丟出去之後由請求管線轉成統一的錯誤格式。

這樣做的結果

  • 登入路徑上，狀態碼小於 500 的失敗（429 除外）都變成同一句 401「使用者名稱或密碼不對」，包括 400（auth.ts:95）。名稱不存在和密碼錯的回應完全一樣（test/m0-db.test.ts）。
  • 429 先判斷，所以被擋的那次就算密碼正確，也是 RATE_LIMITED（test/m2-account.test.ts 的擋猜密碼段）。
  • INVALID_PASSWORD 的判斷不看路徑（auth.ts:96）。
  • Better Auth 的回應 body 讀不出 JSON 時，當成沒有 code（auth.ts:86）。
  • 狀態碼 500 以上變成 INTERNAL，console.error 只印狀態碼和 body.code（auth.ts:102-103）。

為什麼這樣做

  • 登入失敗用同一句：TS-003 §5.3、ADR-0107（auth.ts:94）。
  • 改密碼時目前密碼不對，放在 fields.currentPassword：讓畫面在那一格下面顯示訊息（docs/api/README.md 的 fields 說明、auth.ts:96-97）。
  • 429 變成 RATE_LIMITED 加 retryAfterSec：ADR-0107、ADR-0303。
  • 其他 401、403、4xx 照狀態碼對應：ADR-0107。
  • log 只記代碼，不記 body：程式註解只寫做法，文件沒寫理由（auth.ts:102）。

4 擋猜密碼

要解決的問題

登入只靠使用者名稱加密碼。同一個來源如果能短時間內一直試，就能猜密碼。同一個來源試太多次，要暫時擋下來（TS-003 §5.3）。

怎麼做

用 Better Auth 內建的 rateLimit，明寫 enabled: true，登入路徑 /sign-in/username 設成 60 秒內最多 10 次（auth.ts:67）。來源用 cf-connecting-ip 標頭認（auth.ts:59-60）。超過時 Better Auth 回 429，第 3 段把它轉成 RATE_LIMITED。其他路徑用 Better Auth 的預設值，例如改密碼每 10 秒 3 次（auth.ts:65）。

這樣做的結果

  • 同一個 IP 在一分鐘內第 11 次登入回 429，別的 IP 不受影響（test/m2-account.test.ts 的擋猜密碼段）。
  • 計數存在伺服器記憶體，重開就歸零（auth.ts:66）。
  • 讀不到 IP 時，所有人共用一個計數（auth.ts:64）。
  • 一個家庭或據點共用一個 IP 時，一分鐘內合計 10 次（ADR-0303）。
  • 註冊的次數限制不在這裡，屬於 Account（ADR-0950）。

為什麼這樣做

  • 明寫 enabled：Better Auth 預設只在 production 開，開發和測試也要擋，測試才驗得到（auth.ts:64、ADR-0303）。
  • 依 IP 擋，不依帳號擋：依帳號的話，別人可以故意打錯把你鎖住（ADR-0303）。
  • 計數放記憶體：storage: 'database' 要多一張表，20 人、一台伺服器用不到（ADR-0303、auth.ts:66）。
  • 每分鐘 10 次這個數字：文件沒寫理由，TS-003 §7 只把它列為 v0 想法。

5 帳號資料表

要解決的問題

Better Auth 要存帳號、密碼和登入狀態。使用者要求刪除帳號時，這個人的資料要一起刪（PRD-001 §9.2）。

怎麼做

001_m0.sql:10-59 建 users、sessions、accounts、verifications 四張表。內容是用 Better Auth 1.7 的 getMigrations 照 auth.ts 的設定產生一次，貼進我們的 migration（001_m0.sql:5-6）。sessions 和 accounts 的 userId 都是外鍵，設了 on delete cascade，意思是 users 那一列被刪，這兩張表的對應列跟著刪（001_m0.sql:29、001_m0.sql:36）。

這樣做的結果

  • 密碼的雜湊值（把密碼轉成無法還原的字串）放在 accounts.password，團隊重設指令找的是 providerId = 'credential' 的那一列（reset-password.ts:39-41）。
  • 每支手機的登入狀態是 sessions 的一列，token 欄不能重複（001_m0.sql:24）。團隊重設指令用刪掉這個人的 sessions 列來登出所有手機（reset-password.ts:44）。
  • 這四張表不開 RLS（資料庫依登入者限制能看到哪些列的機制），Better Auth 用自己的連線池讀寫，不經過 forUser（001_m0.sql:7）。
  • 刪 users 一列，私人資料表也跟著刪，因為每張都有 references users (id) on delete cascade（001_m0.sql:8）。

為什麼這樣做

  • 表由我們的 migration 建，不用 Better Auth 自己的 migrate：app 帳號不能建表（001_m0.sql:7、ADR-0106）。
  • 欄位維持 camelCase：改成 snake_case 的話，每個欄位都要在設定裡對應一次，容易漏；我們自己的表只參照 users.id（ADR-0106）。
  • id 用 uuid：文件沒寫理由，TS-003 §7 與 ADR-0106 只寫了這個決定。
  • 不開 RLS：這四張表由 Better Auth 管（001_m0.sql:7）。

6 團隊重設密碼

要解決的問題

帳號沒有真的 email，App 內也沒有自助重設密碼（TS-003 §1）。忘記密碼的人要寫信給團隊，團隊確認是本人後給一組臨時密碼。來要密碼的原因也可能是手機被別人拿走，所以重設時要把這個人所有手機都登出（TS-003 §5.4）。

怎麼做

團隊在自己的電腦上跑 bun run admin:reset-password <使用者名稱>（reset-password.ts:1-6），經 SSH 通道連到資料庫，連線網址放在 MIGRATION_DATABASE_URL。指令先印出連的資料庫（reset-password.ts:97-98），再印使用者名稱、顯示名稱、小學名稱，問一次要不要重設。只有輸入 y 才重設（reset-password.ts:77）。重設時產生 12 字的隨機臨時密碼，換掉密碼、刪光這個人的 session、記一筆事件，三件事放在同一個交易裡。交易是一組資料庫操作，任何一步失敗就整組取消。

這樣做的結果

  • 使用者名稱去掉前後空白、轉小寫再查，所以大小寫不影響（reset-password.ts:26，測試用大寫名稱）。
  • 輸入去掉前後空白後必須剛好是小寫 y，大寫 Y、其他字或空輸入都不重設（reset-password.ts:77）。
  • 帳號沒有小學名稱時，不問、不重設，指令以 1 結束（reset-password.ts:68-72、reset-password.ts:103）。
  • accounts 裡 credential 那一列不是剛好 1 列時，丟出一般的 Error，整個交易取消，session 不會被刪。run 沒有接住這個 Error（reset-password.ts:42、reset-password.ts:52-86）。
  • 事件只記 password_reset_by_team，props 是空的，不含臨時密碼和小學名稱（test/m2-reset-password.test.ts）。
  • 臨時密碼只印在團隊的終端機畫面，小學名稱也會留在那個畫面上（ADR-0309）。
  • 測試確認重設後，舊密碼不能登入，新密碼可以，這個人另一支手機的 token 也失效（test/m2-reset-password.test.ts）。

為什麼這樣做

  • 做成指令，不做成 API：TS-003 §5.4 已決定不做，文件沒寫理由（ADR-0309）。
  • 用 migrator 連線：小學名稱在 account_recovery，後端的 app 帳號被收回讀取權限，只有表的擁有者 migrator 讀得到（reset-password.ts:4、003_m2.sql:31-32、ADR-0300）。團隊也不該拿後端的帳號做人工處理（ADR-0309）。
  • 沒有小學名稱就拒絕：使用者名稱和顯示名稱不是祕密，真正用來確認本人的是小學名稱，沒有它團隊可能只對了兩項就按 y（ADR-0958、TS-003 §4.3）。
  • 用 Better Auth 的 hashPassword：auth.ts 沒有自訂雜湊函式，這樣登入時才對得上（reset-password.ts:36）。
  • 刪光 session：來要密碼的原因也可能是手機被別人拿走（TS-003 §5.4、reset-password.ts:30）。
  • 不從 m0-foundation 的 index 匯入：那會順便啟動 Better Auth、連 .env 的 DATABASE_URL 檢查表，團隊電腦上用不到（reset-password.ts:11-12）。
  • 臨時密碼去掉容易看錯的字：0 和 O、1 和 l 和 I 這種，唸給對方聽、對方抄的時候容易看錯（reset-password.ts:14-15）。
  • 流程抽成 run(db, username, ask, print)：輸入和輸出由外面給，測試才能假裝團隊的輸入（reset-password.ts:51-57、ADR-0309）。
  • 先印連的是哪個資料庫：免得在開發用的資料庫改了半天（reset-password.ts:96-98）。
