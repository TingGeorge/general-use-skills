Table Booking API

Booking tables in one restaurant: what each part is for, how it works, and why

Overview

A small HTTP API that creates, changes, cancels and lists table bookings for one restaurant. Underneath all of it is one rule: two live bookings never hold the same table at the same time.

1 Booking a table

A guest asks for a time and a party size; the API picks the table and stores the booking.

Problem

A request names a time and a party size, not a table, so the API has to choose one (D-03).

Method

Under a lock on the day it lists the free tables, takes the smallest that fits and inserts (routes.ts:58-65).

Why

The smallest fitting table keeps the large tables for large parties (D-03).

Details: 4 results, 2 reasons

Results

  • Tables are never joined: a party of 7 gets NO_TABLE when no single table has 7 seats (rules.ts:41).
  • A 22:00 start is accepted, 22:01 is not (rules.ts:32).
  • The end in the reply includes the 15 clearing minutes (rules.ts:35).
  • Equal-sized tables go by id, so T2 is taken before T5 (rules.ts:42).

Reasons

  • Length by party size: parties above 4 stayed past 90 minutes (D-01, rules.ts:34).
  • Day from the server clock: the server runs in the restaurant's time zone (D-02, routes.ts:35-36).

2 Booking status

A booking moves through five statuses; staff actions change it, and the clock shows a guest who did not come.

Problem

A guest who does not come presses no button, yet the front desk needs to see it (D-05).

Method

Four statuses are stored; statusOf shows a booking still booked 15 minutes after its start as no_show (rules.ts:48-52).

Why

Computed on read, it needs no scheduled job that marks no-shows (D-05).

Results

  • An action the status does not allow returns 409 WRONG_STATUS with the reason (routes.ts:104-105).
  • An unknown action in the URL returns 404 (routes.ts:99).
  • A no_show is still booked in the table, so it keeps its table (store.ts:47-48).

Reasons

  • A no_show can be seated: a late guest still gets the table (D-05, rules.ts:55).

3 No double booking

Two requests for the last free table at the same moment end with one booking and one refusal.

Problem

Two requests that both read "T4 is free" before either writes would both take T4 (D-04).

Method

Every write first locks the booking's day, so one request reads and inserts before the next one reads (store.ts:43-45).

Why

A serializable transaction would abort the second request, which would then have to retry (D-04).

Details: 4 results, 2 reasons, 1 figure

Results

  • A slot ending at 19:45 and one starting at 19:45 can share a table: ranges are '[)' (store.ts:34).
  • Cancelled and completed bookings free their table (store.ts:56).
  • A change leaves its own booking out of the check, so it can stay on its table (store.ts:58).
  • applyAction takes no day lock; it locks only the booking's row (routes.ts:102).

Reasons

  • Constraint as well as lock: it rejects any overlap that gets past the lock (D-04, 001_bookings.sql:32-33).
  • Not the constraint alone: the second request would fail instead of getting the next free table (D-04).

4 Change and cancel

A booking can be moved while it is booked and cancelled until someone seats it; late cancels are marked.

Problem

Guests move or call off bookings, and the front desk wants to see who cancels late (D-06).

Method

changeBooking chooses a table again under the day lock and keeps the old one when it still fits (routes.ts:81-85).

Why

The code comment says the host may have promised the guest that table (routes.ts:82).

Details: 4 results, 2 reasons

Results

  • A change to another day locks only the new day (routes.ts:75).
  • A larger party that no longer fits the old table moves to the smallest free one (routes.ts:83-84).
  • A change needs a future start within seating hours, like a new booking (routes.ts:72).
  • A cancelled booking stays in the table with status cancelled (routes.ts:108).

Reasons

  • Late cancels are flagged, not refused: repeat late cancellers become visible (D-06, rules.ts:73-74).
  • Kept, not deleted: the spec says delete; D-06 keeps the row for the flag.

5 Stored data

Four tables hold the floor plan, the guests, the bookings and each booking's history.

Problem

A booking needs a guest, a table, a time and an outcome, and a cancelled one is kept (D-06).

Method

bookings points at a guest and a table and holds its time as one range, slot (001_bookings.sql:21-38).

Why

A range lets the exclusion constraint compare whole slots on one table (D-04).

Details: 4 results, 1 reason

Results

  • A new booking with a known phone replaces that guest's name (store.ts:62-67).
  • A table set inactive is not offered, and its bookings stay (store.ts:53).
  • The day list includes cancelled bookings, sorted by start, then table (store.ts:94-96).
  • Deleting a booking deletes its events (001_bookings.sql:44).

Reasons

  • No no_show in the enum: it is computed, not stored (D-05, 001_bookings.sql:18).
